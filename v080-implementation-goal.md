# v0.8.0 implementation goal: personal writing tools and an editable Companion

Status: implementation completed on 2026-09-20 on `codex/v0.8.0-personal-writing`. All four workstreams and required gates are complete; see [validation evidence](v080-validation.md) and [live-output findings](v080-output-evaluation.md). The later Skip setup addition and separately authorized 2026-09-21 publication are covered by the [release notes](releases/v0.8.0.md).

## Objective

Make Prospero's Study adapt to the author's writing preferences, make useful workflows reusable, make alternate tellings easier to compare and organize, and let the Sidebar Companion help edit the actual work. An author should be able to select a passage, ask for a revision in a saved style, compare the result, and apply it without copying text between disconnected tools or losing the original.

The release has four required workstreams:

1. Reusable voice and style profiles.
2. Shareable writing recipes and prompt/workflow presets.
3. Branch comparison, favorites, archiving, and cross-branch search.
4. Sidebar Companion pop-out, contextual editing, and conversation improvements.

This document defines the implementation and acceptance goal. The author has activated it and authorized implementation on a new feature branch. Publication remains separate.

## Baseline and scope

Build on the integrated v0.7.5 behavior, including manuscripts and DOCX/EPUB publishing, model controls, agent templates, optional recall, continuity revisions, phrase checks, cleanup, and archive compatibility. Establish the actual branch, release baseline, and existing uncommitted work before editing source; preserve unrelated work.

The current Sidebar Companion is labeled **Collaborator** in the application. These names refer to the same feature, not a second assistant. It already has docked, floating, and full-workspace layouts, saved conversations, source inspection, model selection, and transfer to the unsent composer. v0.8.0 extends that implementation.

Earlier requirements restrict the Collaborator to discussion and proposals. This approved goal expands that boundary to **author-directed text editing through scoped application actions**. It does not authorize autonomous story progression. Update affected product requirements, prompts, permission enforcement, and user-facing explanations together when implementing this change.

## 1. Reusable voice and style profiles

- [x] Add a versioned Library type for writing style profiles, distinct from Character voice and model connection profiles. Support creating, duplicating, editing, naming, archiving, and explicitly adopting a new version in a Story.
- [x] Support prose characteristics, viewpoint and tense preferences, dialogue conventions, rhythm and description preferences, unwanted habits, and author-supplied examples. Keep fields optional and useful without model calls.
- [x] Provide an explicit sample-analysis action that proposes editable style guidance from selected samples. Show the samples used and the generated suggestions; analysis does not silently publish or replace a profile.
- [x] Allow a Story default and an explicit per-request or recipe choice, including no style profile. A per-request choice takes precedence over the recipe choice, which takes precedence over the Story default; an explicit choice of none suppresses inheritance. Display the effective choice.
- [x] Apply the selected style to prose writing and requested revisions, including Companion edits. Task applicability must be explicit: do not inject prose styling into factual extraction, memory bookkeeping, or unrelated specialist tasks.
- [x] Keep samples labeled as examples, separate from story events and Canon. A style preference cannot override branch scope, character agency, source permissions, or required structured outputs.
- [x] Freeze the effective profile version, supplied samples or excerpts, composition, and budget decisions with each request. Profile changes do not alter saved retries or silently restyle accepted prose.
- [x] Offer a reviewable style revision for selected text, using the shared edit/comparison workflow below.

Acceptance example: create a restrained, dialogue-focused profile from the author's samples; use it in two Stories; revise one selected passage; publish a changed profile without changing either Story's pinned version; explicitly adopt it in one Story and verify the other remains unchanged.

## 2. Shareable writing recipes

- [x] Add named, described, versioned recipes that bundle instructions, relevant agent/task switches, routing choices, optional style selection, review lenses, and optional randomness settings. Build on existing templates and routing rather than creating a competing workflow engine.
- [x] Include editable starter recipes for a quiet character scene, revising for tension, and a dialogue pass. Explain the intended target and whether the recipe drafts text, reviews it, or proposes a revision.
- [x] Let authors create, duplicate, edit, archive, and select recipes without requiring advanced prompt editing. Keep detailed prompt and routing controls in the secondary interface.
- [x] Provide typed prompt variables, descriptions, examples, required-value checks, and clear treatment of literal braces and unsupported variables. Story text and imported samples are data, not executable template instructions.
- [x] Preview the effective instructions, style, task sequence, model assignments, source scope, optional calls, and relevant budget limits before a run. Extend previews to the specialist steps configured by the recipe. Unknown provider costs remain unknown.
- [x] Define and display inheritance: existing workspace disables remain a ceiling; explicit run choices override recipe defaults; absent recipe settings inherit applicable Story settings. Merely browsing or importing a recipe changes no active configuration and starts no work.
- [x] Support portable recipe and style-profile file import/export with schema versions, preview, compatibility reporting, and explicit local mapping for missing model or Library references. Include intended sample assets explicitly; omit credentials, private conversations, and unrelated Story data.
- [x] Preserve unsupported settings visibly without claiming they work. Validate the complete proposed configuration before use; imports cannot execute code or silently enable automation.
- [x] Freeze the resolved recipe and dependencies with the request, preserving historical retries even after a recipe is edited or archived.

Acceptance example: export a dialogue-pass recipe and its selected style, import into a clean workspace, map its missing model assignment, inspect the resolved inputs, run it on a selected passage, and verify that later recipe edits do not change the recorded request.

## 3. Branch comparison and curation

- [x] Compare two tellings from the same Story side by side, identify their shared ancestry, and show added, removed, and changed passages with useful text-level differences. Handle historical edits and omission markers without treating identical shared passages as unrelated text.
- [x] Let the author navigate differences, open either source passage, choose which telling to view, and send an explicit comparison or selection to the Companion. Source branch and revision labels remain visible.
- [x] Add branch favorites and reversible branch archive/unarchive controls, with filters and clear archived status. Archiving hides a branch from ordinary browsing; it does not delete history, free source IDs, or invalidate manuscripts, descendants, saved requests, or references.
- [x] Handle archiving the currently open branch without losing selection or leaving a broken workspace. Opening a referenced archived branch must remain possible.
- [x] Add Story-wide cross-branch search with branch filters and an explicit option to include archived branches. Group shared-source matches and show which tellings contain them; retain distinctions for edited or removed versions. Opening a result selects the correct source path and passage.
- [x] Keep broader browsing/comparison permissions separate from writer retrieval. Finding text on a sibling branch does not make it available to the active writer, character lens, or accepted memory.
- [x] Preserve favorite/archive state and comparison source identities through restart and archive restore.

Acceptance example: compare two outcomes of the same scene, locate a changed line, favorite one telling, archive the other, find the archived version through search, and reopen it. Existing book selections and exports still resolve to their originally selected prose.

## 4. Sidebar Companion

### A. Genuine Pop Out

- [x] Add **Pop Out** to open the Companion in a separate same-origin browser window that can move to another monitor. Retain the existing docked, floating, and full-workspace modes and provide an explicit return-to-workspace action.
- [x] Keep the selected conversation, saved replies, model assignment, target context, pending edit proposals, and operation status synchronized across windows. Protect unsent text from conflicting edits; switching presentation must not lose it.
- [x] Prevent duplicate model requests and duplicate edit application when both windows are open. Closing, reloading, redocking, or reopening a view does not implicitly retry or resend an operation.
- [x] Handle blocked pop-ups, a closed parent window, a lost server connection, and an unavailable target with actionable recovery. If the app server remains available, the pop-out can continue independently of the parent view; reconnecting reconciles saved operation status.
- [x] Provide keyboard access, focus return, readable window titles, and narrow-window layouts. Browser-limited window geometry is best effort and is not required to match exact coordinates.

Conversation selection, replies, model choices, source pins, question drafts, pending edit proposals and application receipts now synchronize across presentation modes. A concurrent proposal update preserves unsaved local wording until the author chooses to refresh; simultaneous application returns the same durable receipt.

### B. Contextual work and text editing

- [x] Add **Send selection to Companion** from prose, the composer, supported text editors, and branch comparisons. Include stable source identity and the selected range, with a visible target card rather than an unlabeled text dump.
- [x] Support following the active Story/branch and pinning discussion to a passage, scene, earlier revision, or explicit branch comparison. Changing the main selection does not retarget a running request or a pending edit.
- [x] Offer focused actions such as Discuss, Rewrite, Expand, Shorten, Change tone, Apply style, Check continuity, and Compare tellings. Integrate saved styles and applicable recipes rather than duplicating their settings.
- [x] Implement a shared structured edit action for adding text, inserting before/after a selected range, replacing a selection, and updating a supported text field. Record the target, operation, expected version, original text, proposed replacement, source references, and a concise explanation.
- [x] Support these bounded destinations in this release:
  - [x] Unsent composer text and author notes.
  - [x] Unaccepted prose drafts.
  - [x] Selected accepted passages.
  - [x] Story brief and scene-goal text.
  - [x] Character and Canon text through their existing versioned editors.
  - [x] Style-profile guidance and recipe/prompt instruction text through their versioned editors.
- [x] Distinguish **suggest** from **apply**. Discussion and rewrite suggestions produce editable proposals with before/after comparison and Apply/Dismiss controls. An explicit instruction to apply a change to a clearly selected target can authorize the scoped action without another redundant confirmation. Ambiguous targets remain proposals or require clarification.
- [x] Adding prose is supported: an ordinary request for new wording produces a draft or insertion proposal. It becomes accepted narrative only through an explicit acceptance/application instruction using the normal writing contract. Merely discussing a possible event never appends it to the Story.
- [x] Apply changes to accepted passages through immutable revision/fork behavior, preserving the source telling and exposing the revised path. Preserve or explicitly account for later prose; do not silently drop a suffix. Reconcile affected derived memory using existing revision rules, without replaying rolls or old model calls. Do not silently repoint Book selections to the revision.
- [x] Library and prompt edits create new versions. Publishing and Story adoption follow the user's stated target and scope; editing a shared asset does not silently update every Story that uses it.
- [x] Check exact target identity, version, and selected text at application time. A changed target yields a clear conflict and an explicit rebase/review path. Never guess a replacement range or apply to whichever branch happens to be open.
- [x] Show a durable result with before/after text, destination, originating request, and **Undo/Restore previous version**. Undo preserves subsequent independent work; conflicting undo creates a reviewable inverse change instead of overwriting newer edits.
- [x] Enforce allowed operations and target scope in the backend. Model output alone is not authorization. Conversation data, imported instructions, retrieved passages, and other windows cannot grant broader write authority.
- [x] Retain the Companion's separation from autonomous narrative workflows: no unrequested continuation, plan completion, knowledge changes, story-clock advancement, rolls, workflow approvals, configuration changes, or cross-branch merging. A text edit does not grant permission to modify non-text settings.
- [x] Persist edit receipts and application state. Cancellation, stale results, retries, double-clicks, two-window races, and restart cannot apply a change twice or convert partial output into an accepted edit.

### C. Conversation usability

- [x] Rename, search, archive, and reopen Companion conversations. Archived discussions remain available and retain their source links and edit history.
- [x] Preserve unsent drafts per conversation across presentation changes and reloads; make any scope change visible. Keep navigation, scrolling, and reading positions stable while replies arrive.
- [x] Clearly show effective model, context pin/follow state, selected style or recipe, and whether the current task is discussion, a proposal, or an authorized edit. Keep technical receipts available through details.
- [x] Make only explicitly selected proposal content eligible for transfer. The rest of the side conversation, discarded alternatives, and hidden source material do not automatically enter writer context.

Acceptance example: select a paragraph, pop out the Companion, request a shorter revision using a saved style, compare and apply it, then undo. Repeat with an explicit apply instruction. Edit the same target in the main window while another suggestion is pending and verify a conflict instead of an overwrite. Redock, restart, and restore an archive without losing the conversation, proposal, original prose, or application receipt.

## Shared implementation contracts

- Reuse existing versioned Library assets, prompt composition, routing, operations, branch revision, and archive mechanisms wherever their contracts fit. Define new schemas and migration behavior before coupling the UI to them.
- Preserve exact provider inputs, resolved versions, source scope, reported usage, and acceptance decisions. New profile/recipe instructions participate in context budgeting; no silent loss of required evidence to fit stylistic guidance.
- Keep inherited character knowledge, branch isolation, foreground scheduling, cancellation, and explicit retry behavior intact. Companion comparison access must not leak into another role's request.
- Import/restore validates references and remaps identities. Historical requests keep their original bytes. Restore never replays model calls, reapplies edits, or enables imported automation. Preserve the existing option to exclude private side conversations, while retaining the provenance necessary to validate any included applied text changes.
- Reversible curation does not delete content. Profile, recipe, branch, or conversation archiving cannot break existing pins, manuscripts, receipts, or historical comparisons.
- Use the established visual language and accessible controls. Keep normal writing and simple recipes understandable; expose advanced composition, mappings, and request records through secondary controls.
